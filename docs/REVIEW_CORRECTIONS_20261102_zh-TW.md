目前書面為 [最終結案成品](../paper/README.md)。本次核對既有討論、現行程式、保存的實驗結果與下列原始文獻，修正研究範圍和說明，沒有新增實驗或更換演算法。歷史書面、規約與原始封存保留原樣。

## 下一步

保留的研究提案是增加觀測點，研究差異出現在哪一段。目標為對齊同一次完整列舉的三份資料：核心已接受項目、getdents64 回傳記錄，以及程式經函式庫取得的項目，再比較相鄰兩端的摘要。

這項提案尚未實作。glibc 會批次讀取系統呼叫資料，再逐筆交付，因此一次函式庫呼叫與一次系統呼叫並非一對一。須先建立同一程式、同一開啟目錄及列舉區間的配對，處理未讀完、缺記錄與失效，再驗證正常列舉、核心過濾、函式庫過濾及成本。差異區段不等於惡意來源。[glibc 2.35 原始碼](https://github.com/bminor/glibc/blob/glibc-2.35/sysdeps/unix/sysv/linux/readdir64.c)

一般程式監控、辨識掃描器的攻擊者、金鑰保護、單純換成 /proc、掃描整個檔案系統、預編譯，以及再增加工具或環境，不另排為本研究的下一步。有限容量與重複差異仍是方法限制，還原核對與入口漏失拒判則已完成。原有的第一觀測點之前視圖與授權分類也沒有加入。

## 方法與結果的修正

| 問題 | 修正後的說明 | 依據 |
|---|---|---|
| 回傳欄位改寫容易被理解為實際改檔案 | 差異動作中的新增、改名、inode 與型態是回傳記錄的操控。正常動態試驗才實際建立、改名及刪除檔案 | 論文 5.5、受控模組與獨立預期差異核對 |
| inode／型態的研究理由未說清楚 | 這些是程式會使用的回傳資訊。PEP 471 說明可利用列舉型態省去查詢，glibc 2.35 原始碼會略過零 inode 記錄 | [PEP 471](https://peps.python.org/pep-0471/)、[glibc 2.35](https://github.com/bminor/glibc/blob/glibc-2.35/sysdeps/unix/sysv/linux/readdir64.c) |
| 從上述例子直接宣稱受測 ls 或遍歷工具會被隱藏 | 程式依據說明影響後續處理的理由，現有實驗只驗證欄位差異。未測受測套件、ls 顯示或遞迴遍歷的效果，也未據此宣稱實際 rootkit 已採用 | 文獻與受測操作分開，不新增實驗成果 |
| 把 h₂ 視為獨立檢查並相乘成統一碰撞率 | h₂ 沿用 h₁。只換名稱且 inode、型態相同時，h₁ 相等會使 h₂ 相等。多筆差異雖多一項總和檢查，非線性本身不能證明獨立或給出所有輸入的機率上界 | [共用雜湊定義](../collector/d9_reconciliation_hash.h)、[指紋實作](../src/kicba/reconciliation.py)、論文 4.1 |
| 固定摘要被說成固定掃描成本 | 固定的是指定容量下的摘要 bytes。每項仍須讀取、雜湊及更新，耗時隨項目數增加。小目錄與中大型目錄的結果分開，完整程序成本與掃描判讀成本分開 | [逐筆記錄成本](D9_CONFIRMATORY_RESULTS_zh-TW.md) |
| 重複開機或背景負載被寫成新增偵測能力 | 小緩衝區與巢狀包裝檢查計入規則。負載、種子及順序變化檢查實作重複性，九次開機仍是同一環境 | 論文 5.2、6.1–6.2 |
| 量測可信被寫成已能抵抗核心攻擊者 | 可信量測仍是範圍假設。可取得的入口、返回及 BPF 統計已接入拒判，但不能保證任意故障均可見，也不能由系統保護機制推得核心對手無法干擾 | [量測品質與比較核對](METHOD_CLOSURE_20261102_zh-TW.md) |
| 合法政策過濾被擴成授權分類研究 | 本研究只判斷身分是否一致，政策過濾也是差異。原因可依可信政策或過濾紀錄解釋，授權分類不加入本文 | 論文 3.2、7 |
